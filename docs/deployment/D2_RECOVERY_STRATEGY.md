# D2 recovery strategy

Use a hybrid model as Ayinou moves toward a private pilot. First establish independently controlled, encrypted database and Storage copies in a private recovery account. Add verified provider daily backups when the owner approves the required plan and actually sees a usable recovery point. Buy PITR only when the accepted data-loss objective cannot be met by scheduled snapshots or when public-launch risk warrants it.

| Option | Recovery point and completeness | Cost and operations |
| --- | --- | --- |
| Provider daily backup | Database and platform-managed restore path. Expect up to the interval between successful snapshots. Storage bytes and independently managed configuration need a separate recovery path. | Paid-plan inclusion and retention depend on tier. Provider simplifies database restoration. Availability, operator access, time and results still need independent verification. |
| Provider PITR | Database recovery within a verified retained WAL range, down to seconds under supported conditions. Storage still needs its own matched recovery point. An in-place restore displaces newer database changes. | Paid add-on and supported compute. Review cost, downtime, WAL coverage, alternate target and data loss before buying. |
| Independent logical backup | Versioned database schema, selected rows and manifests at each successful snapshot. Portable within compatible PostgreSQL/Supabase targets with tested ownership and Auth handling. No arbitrary point-in-time replay. | Private storage, egress, execution, key custody and operator time. More restore work and independent validation. Owner approval needed before the first hosted export. |
| Hybrid | Independent recovery copy if provider access fails, plus provider-managed database path when verified. Recovery is limited by the older of the matching database, object and configuration checkpoints for affected data. | Two systems to operate. Keep keys and credentials separate, reconcile scope and check both forms of restore. |

## Database capture and handoff

1. Pin the exact approved source, compatible PostgreSQL tool/database versions and allowlisted schemas. Verify the project ref before connecting and restrict the worker to the approved read scope. A native custom-format dump or Supabase-supported logical workflow is appropriate after scope is approved. Use TLS with verified endpoints and use a provider-approved connection compatible with dump tools. Keep the connection string and password in the approved secret store.
2. Cover application schemas, functions, triggers, ACL and RLS definitions, app-defined roles and grants, migration history, audit, verification provenance, institutions, projects, polls, legal and privacy state. Compare an inventory against the archive. Export supported Auth data only with explicit custody authorization. Verify what the provider's logical workflow excludes from managed Auth/Storage schemas, and rebuild required platform defaults using supported tools before loading compatible data. Keep migration-history data and role definitions as explicit, reviewed artifacts where the backup mechanism omits them.
3. Restore and check required extension availability, versions and ownership. Cluster globals, certain managed roles, passwords, signing keys, encryption roots, integrations, restore destinations and provider options need separate custody or recreation. Never assume a successful database dump includes Storage bytes, OAuth secrets, SMTP credentials, provider configuration, worker secrets or the ability to use old JWTs.
4. Encrypt before custody transfer with an approved authenticated encryption or envelope-encryption mechanism. Keep a restricted, authenticated manifest with point time, source alias, migration and tool versions, object counts, SHA-256 and key ID. Store the key and ciphertext with separate least-privilege access. Verify digest and decryptability, test restore independently and audit capture, access, restore, rotation and expiration without copying raw user data, connection strings or keys into Git, GitHub Actions, tickets or logs.
5. Match database scope with the Storage manifest and independent Auth/configuration record. Preserve post-checkpoint change windows and reconcile latest revocations, rights requests, evidence holds, suppression and audit receipts before release. Keep recovered environments private, isolate credentials and disable email, integrations and public traffic. A provider binary clone can start copied jobs and external-capable extensions immediately. Review them before approving a clone. If egress cannot be contained before it starts, use a reviewed logical restore that allows inspection before enabling workers. Reissue or invalidate sessions under approved policy. Apply unfinished reviewed migrations forward only after verifying the migration ledger and effective guards.

The D2 logical rehearsal uses a fresh database in a disposable local cluster with roles already available. It is a narrow tool and integrity check. Production scope, cross-cluster role reconstruction and provider restore require separate evidence.
