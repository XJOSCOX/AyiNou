# D1 database security review

The line of authority starts with Supabase Auth and the authenticated actor. Service RPCs receive a server-verified identity and recheck scoped access where supported. RLS and explicit grants constrain alternate access. Product success events and receipts remain in their domain transactions.

| Migration | Structure, permissions and data preservation | Risk and release check |
| --- | --- | --- |
| O2 | Three RLS-enabled private tables. Foreign keys bind the signup choice, open intent and receipt to their subject. Partial unique open-intent index and unique subject/request receipts preserve one workflow and deterministic replay. The Auth insert/confirmation trigger captures an organization choice only for confirmed signup. | Adding a trigger takes a lock on `auth.users`. Confirm the existing referral trigger, new trigger and confirmed personal and organization signups. Keep restarts paused if trigger errors appear. |
| O3 | Five RLS-enabled private tables. Scoped grant ties subject and policy to an authority, case and proof with foreign keys, unique/current case checks and durable provenance. MFA, conflict and issuer checks gate privileged work. The issuance predicate is false. | Restrictive foreign keys protect evidence and may affect future deletion. Verify no scope or proof was seeded. Test closed issuance and public projection separately from identity. |
| O4 | Adds private registration with default `unknown` and version zero. Preserves all prior owner and organization rows. Extends intents and institutional audit, replaces the open-index predicate and adds unique command/declaration keys. Independent identity, authority declaration and current scope guard completion. Claim approval still requires two distinct eligible reviewers with matching institutional state. | ALTER TABLE takes strong locks on organizations, onboarding intents and institution audit. New indexes on existing audit data can block writes and validate uniqueness. The old create path becomes unavailable when O4 commits. Keep signup and legacy institution/claim commands paused across O2–O4. |
| O5 | Six RLS-enabled private governance, correction, hold and event tables. Versioned consent and proposal transitions have distinct actors, role and recent MFA checks, protected dependencies and atomic receipts. The one seeded row is bootstrap, with no authority grant or high-impact execution. | Claim decisions share a transaction lock with holds. A retry must respect expiry, current roles and dependencies. Preserve all events and holds in recovery. |
| O6 | Five RLS-enabled private tables protect program configuration, scoped operators, enrollments, feedback and audit. Keys and indexes protect reservation and command scope. Independent operators, live owners, consent and expiry are part of the state machine. The production synthetic gate returns false and no program is seeded. | The serialization lock also coordinates O5 decisions. Keep public designations and live enrollment closed even if an operator possesses ordinary administrator access. |
| O7 | Replaces four existing routines without new storage or signatures. Uses the decision clock for live sessions and invitations, locks the user before their session and rechecks authorization before replay, and records the invitation decision time in the audit trail. | Watch for lock waits, deadlocks and retry errors. Definition replacement alone does not run existing commands or rewrite data. Confirm the replacement, current grants and exact versions. |

Private tables have RLS enabled and application-role grants revoked. The migration review examined references, uniqueness, indexes, restrictive lifecycle effects, schema-qualified routines and explicit empty search paths for privileged definitions. End-to-end catalog tests check 19 private tables and 16 restricted RPCs. Existing public and owner access is exercised separately. Secure recovery must preserve function grants, domain receipts and restrictive evidence links.

## Atomicity and failure semantics

The six files are ordered migration units. Each committed version is recorded by the migration runner. Directly replaying files with create statements or O4’s index replacement can fail on existing objects. Use the migration history to identify pending versions. A disposable failure injected after O3 rolled back the failing file and did not start the apps. After removal of the temporary file, the same database resumed through O7. On failure, stop, check the last recorded version and effective catalog, and keep the write pause active. Avoid manual history repair and destructive down SQL. A proven compatible application rollback keeps the O4 guard in place. [Approval checklist](D1_DEPLOYMENT_APPROVAL_CHECKLIST.md)

## Outstanding verification

A sampled catalog and disposable role tests establish the reviewed boundary. They do not cover every legacy customer data scenario, production lock timing or every concurrent schedule. Before any release, repeat read-only checks against the exact project, compare staged DDL with the approved hashes and confirm no production data or provider control changed in the interim.
