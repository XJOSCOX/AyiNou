# Administrator activation

| Owner-approved requirement | State at baseline |
| --- | --- |
| Only the recognized Founder can initiate an Administrator appointment. A normal admin can perform routine management and grant permitted lower roles. | **Implemented in F1 source and disposable SQL.** The wrapper enforces Founder-only `appoint`. **Implemented but disabled on hosted development** until F1 ships there. Pre-F1 O5 permits eligible administrators to propose and keeps general execution closed. |
| Use a written reason, exact target UUID, live Founder session, recent TOTP and eligible candidate. | O5 provides versioned proposals and decisions. F1 issuance rechecks the proposal and current Founder, the target’s active account, independently reviewed identity and verified TOTP. An invitation alone confers no role. |
| Require independent O5 approval from a different eligible and unconflicted Administrator. | **Owner approved and implemented in F1 source.** The approver uses a live session and recent MFA and records a reason and conflict clearance. The proposer and candidate cannot approve. Without an eligible independent Administrator, the appointment stays pending. There is no automatic Founder-only approval exception. |
| Give only the intended account a high-entropy, single-use code. | **Implemented in F1.** One invitation per proposal, 32 random bytes, hashed verifier, expiration at the earlier of 24 hours or the proposal deadline, five failed guesses once eligible to redeem. The issuing Founder sees the code once. Delivery is manual via a verified private channel. No email or SMS delivery is implemented. Operational custody and delivery procedures need **approval**. |
| Activate only after Founder initiation, independent O5 approval, and explicit acceptance using the selected member’s own authenticated account, fresh MFA and one-time credential. | **Implemented in F1.** A single transaction rechecks current Founder and approver eligibility, target UUID, active account, identity, verified TOTP, live session, proposal revision context, approval, expiry and the code. It records acceptance and green-role assignment, consumes the verifier and writes audit. Copied links, other accounts, stale or revoked state and concurrent replay cannot activate. |

## Entry points and outstanding integration

- `/admin` → Platform Governance owns O5 proposal and approval. `POST/DELETE /api/v1/admin/appointments/:id/invitation` issue and revoke by proposal. `/activate/a/{id}` and `GET/POST /api/v1/administrator-activation/:id` present the subject’s status and redeem with explicit acceptance. Delivery divides the opaque link from the separate code.
- The target can see pending approval, and access from an unrelated account receives a generic result. Existing O5 proposal-only acceptance still exists. It can record acceptance independently of redemption and never grants the role. For a future UI pass, present one active acceptance path for F1 appointments and retain existing O5 historical receipts.
- Issue-once means a lost issuance response cannot recover the code. Revoke or withdraw the old invitation/proposal and use a newly reviewed proposal where appropriate. A future reissue policy needs **owner decision** and explicit authorization versioning. Expiry is enforced on access and expiration audit is recorded when an eligible request observes it. Generic execution, administrator removal or suspension through protected O5, succession and recovery stay disabled.
- **OWNER APPROVED — NOT YET IMPLEMENTED** for S2 session enforcement. The recognized Founder and active Administrators have a six-hour absolute ceiling from original authenticated session start, regardless of Remember This Device. Before privileged access, revoke or constrain pre-promotion sessions so the new Administrator never inherits the ordinary 30-day deadline. Revocation removes administrative authority immediately. Applicable actions retain the shorter 15-minute TOTP freshness check. F1 deployment and S2 enforcement are separate work.
