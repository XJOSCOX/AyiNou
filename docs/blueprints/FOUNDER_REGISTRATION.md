# Founder registration

| Owner-approved design | Observed status and limits |
| --- | --- |
| The first eligible account established through trusted installation setup becomes the unique Founder. | **Implemented.** The committed bootstrap singleton and matching security event identify a specific Auth UUID. An ordinary first signup, environment change, profile handle, email, public badge or editable grant conveys no Founder authority. An initialized installation keeps its existing Founder. |
| Reserve the configured handle and mailbox privately. Require a dedicated secret-first setup before showing Founder signup controls. | Reserved identity and provenance are **implemented** and deployed through U1. The F1 schema is deployed on hosted development. Enrollment is unavailable there because the existing Founder is already established. The operator script requires explicit configuration and a new output file stored outside the repository under restricted access. |
| Require real mailbox control, a live eligible session and fresh MFA. Consume the authorization exactly once and preserve provenance. | **Implemented and validated in disposable F1.** Auth auto-confirmation blocks private F1 signup, and SQL checks proof provenance and the staged Auth account before claim. Existing hosted Founder provenance keeps setup closed. Verify production email delivery and operator storage separately. |
| Founder automatically inherits eligible routine administration and the red role badge. | **Implemented.** Effective operational authority needs a live eligible account and verified authenticator plus action-specific assurance. Role recognition creates neither a blue independent identity mark nor a gold Founder Verified mark. |
| Provide safe succession and recovery without unilateral promotion or losing historical evidence. | **Not implemented** for execution. O5 has proposals, approvals and recovery authority representations. Execution stays closed. **Owner decision and operational approval** for successor, independent adjudication, revocation and recovery. |

## Fresh installation path

1. Confirm the intended environment and that trusted Founder provenance is absent. From a private operator environment, use `scripts/prepare-founder-registration.mjs` and the `AYINOU_FOUNDER_BOOTSTRAP_ENABLED`, `AYINOU_FOUNDER_EMAIL` and `AYINOU_FOUNDER_USERNAME` configuration. Deliver the opaque `/setup/f/{id}` path and its separate 32-byte random credential through controlled channels. The private SQL reservation stores a verifier, a 30-minute expiry and an attempt cap of five.
2. Enter the credential in the private form. A successful exchange sets a separate random, protected authorization in a path-scoped HttpOnly cookie. A copied path proves nothing. Unlocked form reads check the verifier and the original expiration. HTTPS is required on a hosted installation.
3. The server submits Supabase signup using the configured email and workflow-specific staging username. The member follows the real emailed confirmation, returns through the allowlisted callback and completes TOTP. The original browser can resume within the deadline. The operator can rotate the challenge for the same reservation after interruption.
4. The transaction checks the exact staged account, actual email proof, live session, fresh TOTP, current eligibility and empty trusted bootstrap. It claims the reserved username, suppresses the staging alias, commits Founder provenance and clears the authorization. Subsequent visits are generically unavailable.

**Compatibility.** Older Account Settings enrollment documentation describes a legacy path. The F1 SQL disables that path as soon as the dedicated flow is prepared while preserving its legacy behavior before preparation. Recommend deciding a retirement point after compatibility and recovery tests. An existing trusted Founder skips fresh-install preparation. A second account must never acquire competing provenance.
