# I1 recommended development sequence

| Sequence | Deliverable | Dependency |
| --- | --- | --- |
| Parallel release readiness | Resolve live poll privacy, recovery, Auth/SMTP, legal, retention, staffing, configuration and incident gates. | Founder decisions, counsel, infrastructure and operating owners. [Launch dependencies](I1_LAUNCH_DEPENDENCIES.md) |
| C1 | Pilot reviewed needs and evidence within authorized communities. | Community membership, consent and disclosure rules, staffed reviewers, evidence handling, retention and appeal decisions. |
| C2 | Validate outcomes independently and publish privacy-safe impact measures. | Stable needs/project links, outcome evidence and reviewer conflicts policy. |
| C3 | Build opt-in volunteer skills and matching atop opportunity and task flows. | Project team permissions, skills vocabulary and member-controlled disclosure. |
| Later | Add trusted media and opportunities/mentorship after governance and safeguarding design. | Source rights, editorial review, corrections and staffing. |
| Later | Assess financial contributions, transparency and native mobile investment. Measure web accessibility and low-bandwidth behavior earlier. | Legal/accounting controls and recovery for finance. Member usage and connectivity evidence for native. |

## Proposed C1 scope

- Give a member in an eligible community a way to file a local need with a plain-language description, broad location, suggested audience and references. Avoid collecting precise private location. Use existing community visibility and identity controls.
- Make triage and review explicit. Support duplicates, provenance, reasoned decisions, correction history and withdrawal. Capture editor and reviewer identities within the authorized case. Define how disclosures and redactions appear to the community.
- Provide a scoped, independent review lane with an authority and conflict check. Agree a correction or contest route before public pilot. A verified identity can help establish who is participating. Evidence review establishes what the record supports.
- Pilot an optional reviewed-need link in the existing project proposal after the core need record works. Enforce access on both sides and prevent the link from widening either audience. Proposal review, publication and project work keep their existing lifecycle.
- Prove reviewer scope, required reasons, versioning, visibility, withdrawals, conflict rules and safe reuse with disposable and connected read-only verification plus authorized test actions in a disposable environment. Get an explicit operating decision before exposing a live pilot.

C1’s proposed boundary ends at the reviewed need and an optional project link. Independent outcome accreditation and a community impact dashboard depend on C2. Public-claim review outside the need workflow, a station directory, a new finance system and a native application are later decisions. I1 makes no C1 implementation changes.
