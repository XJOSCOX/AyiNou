# Founder Verified standing issuance

## Scope

The recognized Founder can open a case and verify any eligible, consenting member in Ayinou after the standing policy is activated. The owner approved eligible-member scope and retained each existing verification protection. No independent blue, role, legal, privacy, polling or project criteria change.

## Data model and API

The private approval registry gains a standing scope. Its approval has no per-member cohort or expiry. The historical test scope keeps its original bounded windows and membership. The application reuses the current APIs and session-bound member confirmation. The interface explains when it is waiting for the member or the current policy excludes the account.

## Permissions and audit

The Founder must still use recent TOTP within the privileged session and the original private Administration workspace. The recipient must consent and complete the current session-bound challenge. Attestation and issuance retain existing authorization, case version, scope and transactional audit checks. Operations owns approval and emergency stop. There is no policy-editing app or service grant. Historical grant eligibility checks the original approved policy and proof lineage.

## Privacy and lifecycle

The existing consent, disclosure, records and evidence boundary remain in force. Independent reviewers continue to own contested decisions. Holds, withdrawal, revocation and the existing closure of only the explicitly consented regular application remain in the authoritative ledgers.

## Localization and accessibility

Case status feedback uses the existing semantic status and form controls with Haitian Creole, French, English and Spanish messages.

## Reliability and recovery

Confirmation uses the same transaction lock as policy cutover and grant to prevent cross-policy proof. In-progress proofs must be confirmed again on cutover. Existing grants retain provenance through the cutover. An emergency stop cannot reactivate a legacy cohort. Restore operating eligibility only under a new approved policy.

## Validation and CI

Six focused disposable Chromium regressions passed. They covered transition from the test policy, historical grant visibility, successful issuance without a cohort row or recipient authenticator, independent approval boundaries, and emergency stop while the old test window was still open. Hosted rollout requires tested main, all three CI jobs, an exact migration dry run and the authorized policy operation.
