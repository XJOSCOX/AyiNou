# U1 signup and availability

Both existing signup choices create one personal Supabase Auth account and collect the member’s public username there. The responsive form keeps the swipeable individual and organization choices, password and confirmation controls, referral field, email confirmation and the existing auth shell. Username and email sit on the same row when space allows and stack on phones. The username supplies the initial public display name. The language selector beside the theme control supplies the preferred account language. Members can change both values in their profile later. The form shows a handle preview, a 350 ms debounce, live text status and a suggestion that is checked independently. Changing the input or leaving the page cancels obsolete checks. The Auth transaction makes the final decision.

`GET /api/v1/usernames/availability?username=<handle>` returns only `{ "status": "…" }`, with `available`, `taken`, `invalid`, `reserved`, `blocked`, or `unavailable`. `taken` applies to a publicly eligible profile. Private occupied names, live leases, former names, manual safety holds and the protected Founder reservation use the generic `unavailable` status. Malformed input receives `invalid`. There are no identity, status, or reservation details in the body. Requests are uncached and use a dedicated bounded username category in the existing read budget. Availability uses sanitized route-level diagnostics and no durable per-query event.

If another applicant claims the name before signup commits, the form refreshes availability and preserves the entered details for correction. Leaving the form before submission creates no lease. An abandoned pending signup releases the name automatically after 24 hours. A late email confirmation remains valid. If the lease expired or was lost, onboarding collects another available username. Existing confirmed administration and invitation provisioning remain supported. Keep Auth email confirmation enabled when deploying.

`POST /api/v1/admin/usernames/review` accepts `requestId`, `action`, `username`, `reason` and `replacement` only for a correction. Actions are `hold`, `release`, `correct` and `appeal_reviewed`. Reason codes are `impersonation`, `abuse`, `false_positive` and `safety`. The endpoint requires recent TOTP and a live platform administrator. The database rechecks both, protects authorized identities, and returns an idempotent `receiptId` and event. Initial case intake remains manual.
