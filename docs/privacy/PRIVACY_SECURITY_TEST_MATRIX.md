## Additional coverage and known gaps

The supplemental check ran from an ignored disposable copy. It composed the checked-in [intake](../../apps/web/e2e/privacy-intake.spec.ts), [export](../../apps/web/e2e/privacy-export.spec.ts) and [lifecycle](../../apps/web/e2e/privacy-lifecycle.spec.ts) fixture helpers with the checks below. It used real local Auth/TOTP and guarded SQL on the runner's dedicated database. The first two supplemental attempts failed due to fixture input and parsing errors, corrected in the harness before rerunning. They did not establish a product defect.

| Journey steps | Expected and observed result |
| --- | --- |
| 1–3. Register fictional subject, establish session, enroll and verify MFA | A confirmed Supabase Auth fixture with initialized member profile signs in and verifies TOTP. The same stepped-up subject continues through intake, export and closure. The fixture registration uses the local Auth admin helper. |
| 4–7. Submit, check receipt, retry, conflict | Both API processes return the same 201 receipt for one key, owner history contains one version-one received event, a different member gets 404 and a changed payload returns 409. Injected subject reference gets 400. |
| 8–11. Create export, generate, validate JSON, download | The owner receives field-allowlisted JSON with a category count and recomputed SHA-256 for every item in the manifest. Omitted data stays absent. Database custody holds an authenticated ciphertext. A second random key cannot decrypt it, an unsupported version fails, and resealing with the replacement key rejects the old key. This exercised the package layer with a real synthetic artifact, not a production rotation mechanism. |
| 12–14. Revoke, deny, reconcile | Stop between read and release, revoke through Fastify and confirm release fails. The terminal row is cleaned/revoked, ciphertext is null and the denied release does not increment successful downloads. A separate export withdrawn after lease claim cannot finish or deliver. |
| 15–17. Open closure and deletion cases, plan, test ownership | Institutional ownership appears as a blocker for the fictional subject. The fixture transfers ownership to a different person for the separate closure plan. Duplicate plans coalesce and stale versions fail. |
| 18–19. Holds and independent releases | Two holds on the same scope block approval. The placer cannot release either hold. The case-scoped releaser clears them separately. One release leaves the other hold in effect. An unrelated private actor cannot place a hold on a different subject. |
| 20–22. Marker execution, simulated interruption and recovery | Independent approval gates execution. Abandoned leases need reconciliation. A stale lease and a late hold stop effects. An injected rollback leaves the marker unchanged; retries reconcile and the atomic audit records only the two successful effects. |
| 23–25. Quarantine, suppression and release | Synthetic markers reappear, force quarantine, are suppressed by the restorer and enter release review. The approver fails before reapplication, the restorer cannot release, and an independent approver clears quarantine only after reconciliation. Auth and profile rows remain. |

The supplemental boundary probes used an ordinary subject, another active member, a platform administrator, an organization editor and affiliated staff member, a verification reviewer and a member assigned to the reserved privacy case table. Each non-subject received 404 on the case and 403 on the triage API and direct authenticated lifecycle RPC. Separate scoped hold placement, release, approval, execution and restore fixtures gained only their assigned operation through the service role.

The browser lifecycle fixture demonstrates representative and group ownership data in the graph and tests the approval, hold, execution and restore identities separately. Organization/community project parent ownership, all pending invitation types, every verification-appeal form, all resource-level hold rules and the completeness of the indirect dependency inventory were not independently exercised per subtype. Keep unsupported categories blocked in a future real export or deletion policy until their behavior is demonstrated.

The tests cover secret-bearing surfaces through output schemas, redaction code, authorization probes and decoded synthetic archive assertions. The successful local suite and supplement logs had zero token, service key, TOTP URI or fictional email signature matches. Tests did not exercise production telemetry or vendor log sinks. Do not publish fixture trace files. Counts-only evidence is appropriate for shared CI artifacts.

After a network or unknown outcome, read the receipt, artifact state or step journal before retry. A database release barrier can deny future delivery. It cannot unsend bytes already delivered. PostgreSQL cleanup is neither provider erasure nor proof of deletion from backup.
