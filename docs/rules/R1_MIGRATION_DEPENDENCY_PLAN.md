# R1 migration dependency and future test plan

This is a proposal. Each later stage has its own implementation, disposable rehearsal, full regression, GitHub CI, exact hosted migration authorization, postflight and closure.

| Order and integration | Source dependencies | Data/API and user impact | Release checks |
| --- | --- | --- | --- |
| 1. Registry definitions and read-only resolution rehearsal | AGENTS, S1, AUD-01, RUN-01, SES-02/04 | Define typed registry and safe read contract in a future stage. Seed controlled definitions in disposable only. No current feature consumes settings during shadow comparison. | Existing behavior match by fixtures, unknown keys fail closed, cross-scope denies, bounded reads, stale invalidation, basic localization. |
| 2. One low-impact operational control | FED-05, SOC-03 or a scoped listing budget from RUN-02 | Introduce one approved value through existing authority and apply hard safety envelopes. Version existing default without changing behavior. Avoid adding broad policy-write endpoints. | Authorization for amendment, draft/activation race, idempotency, expiry/rollback, offline fallback, resource metrics, four locales. |
| 3. Domain product settings | ACC-02, COM-03, ORG-03, PRO-02, POL-03 | Add one domain at a time. Preserve existing schema checks. Pin case or expiry where needed and keep route contracts stable. Report changed owner/manager workflows. | Membership and domain RLS, validation parity, replay, concurrent writes, supported UI and protected role isolation. |
| 4. Governed case policies | BLU-04/05/06/07, PRO-01, GOV-01/02, GLD-03 | Add revision references to new and clearly identified pending decisions only according to approved transitions. Backfill provenance only if verifiable. Keep old outcome receipts intact. | Two/three approvals, conflict and hold enforcement, exact-case scope, comparison against existing independent decisions, rollback as new version. |
| 5. Legal, privacy and high-risk visibility | LEG-01/02, PRI-01/02/03, targeted protected feature controls | Reuse or link approved native policy/registry systems. Start with permitted visibility. Keep real gates guarded. Data retention or processing requires separate approval and proof. | Empty registry and draft isolation, private data and ballot boundaries, hold/release and stop authorization, independent approval and least privilege. |

Environment and bootstrap controls stay outside these migrations. Direct Founder blue and existing ordinary/gold behavior are characterization baselines. Session expiration, recent factor freshness and evidence access remain enforced in all stages. Avoid replacing the current application’s live protected paths with fallbacks that can widen authority.

For each stage, run disposable SQL allow/deny and race cases for actor, case and workspace. Validate policy read and write authorization, concurrent activation, default and missing-revision behavior, stable deadlines and in-flight policies, new-version rollback, cross-domain privilege isolation and historical integrity. Run API, Chromium, four-language and accessibility checks, both builds, privacy/ballot isolation, legal integrity and CI on the exact release. Use read-only hosted preflight, verify checksum and dry run, apply only the explicitly approved migration, then recheck role/gate state and remaining migrations. Keep development rollout separate from public launch.
