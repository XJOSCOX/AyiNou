# F1 private Founder registration

An operator on a fresh installation can run the existing `scripts/prepare-founder-registration.mjs` with the private Founder enrollment configuration and a new restricted output file. The file holds the opaque `/setup/f/{id}` path and a separate 256-bit code. Deliver the path and code separately. Keep the file in restricted operator storage and dispose of it after delivery. The server retains a SHA-256 verifier, a 30-minute deadline and five attempts.

The server exchanges a valid code once for a separate 256-bit authorization stored in a path-scoped HttpOnly cookie. Only that authorization reveals the fixed email and reserved handle. The server submits a normal Supabase signup using a staging handle bound to the workflow. The callback allows the exact private path and keeps the existing Supabase PKCE session. A final transaction checks the original workflow, the registered account, actual mailbox proof, current session, recent TOTP and the bootstrap singleton. It promotes the reserved username and commits existing bootstrap provenance atomically. An already initialized installation presents a generic unavailable page.

Signup is blocked in the private Founder form while Auth auto-confirms email. Ordinary development signup can still use that setting. Existing trusted Founder provenance continues to authorize the original account. An interrupted workflow can resume with the same browser authorization or an operator can rotate an expired or exhausted reservation without changing the staged identity. Restarting the setup does not transfer the existing Founder.
