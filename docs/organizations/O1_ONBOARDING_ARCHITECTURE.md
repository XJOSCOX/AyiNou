# O1 organization onboarding architecture

Design proposal against main at `b184fdfc7630457a55471349881097c8dffabd63`. See the [implementation sequence](O1_IMPLEMENTATION_ROADMAP.md) and [owner decisions](O1_OWNER_DECISION_BRIEF.md).

## Existing entry points

- `auth-screen.tsx` calls Supabase Auth signup. `app/auth/callback/route.ts` exchanges the code and routes to personal onboarding. `features/profile/profile-editor.tsx` persists the personal, location, public profile and interest steps with `onboardingStep` through the member API. Keep that sequence for both paths.
- Phase 2C captures validated referral attribution on Auth insertion and confirms it at member initialization. Member and referral codes live in separate private tables. Neither is an invitation, age proof, identity proof or organization credential.
- The Institutions hub calls `POST /api/v1/institutions`. The effective Phase 5D `institution_save_for_api` create branch inserts an active institution and owner membership together for an eligible actor without reviewed identity. Direct API callers must be gated alongside UI callers in O4. Phase 2D uses a globally unique normalized handle, one nonrevoked owner and one nonrevoked foundational relationship per user and organization. A user can hold relationships in multiple organizations. Affiliations, custom roles and foundational roles serve different purposes.

## Flow and recommended source copy

| Screen | Decision, behavior and copy |
| --- | --- |
| Entry | Radio group headed “How would you like to start?” Individual: “Create a personal account.” Organization: “Create a personal account and start setting up an organization you are authorized to represent.” Both use the same eligibility rules. |
| Account and email | Reuse signup and callback. “Confirm your email to continue. Identity review is a separate step for organization setup.” Finish applicable account requirements and save the selected path for the authenticated subject. |
| Personal onboarding | Finish or resume regular profile steps. “You can use Ayinou as a member while you prepare your organization.” Member access follows current account and any future pilot rules. |
| Identity gate | “Confirm your personal identity before you finish organization setup.” Show eligible pathway, pending or held status, retry guidance, private draft and “Continue as an individual.” Offer independently reviewed identity and only an approved Founder Verified path. |
| Resume | “Resume organization setup.” Reload the actor’s current draft and eligibility from the server after reauthentication. Reevaluate before every decisive write. Clear cached subject data on sign-out or account switch. |
| New or existing | “Create an organization” or “Request to manage an existing organization.” Suggest publicly discoverable matches without revealing hidden records. Link an invited representative to the existing invitation flow. |
| Organization form | “How is this organization registered?” Explain “Informal or unregistered” and “Registration in progress.” Permit a blank registry reference. A registered claim remains private until approved for display. |
| Authority and finish | “Tell us why you’re authorized to manage this organization.” For new ordinary organizations require a declaration and the approved evidence/risk checks before initial ownership. Existing claims use assigned review. Show a pending receipt and an optional organization verification application after setup. |
| Correction | “Change how you started.” Show what the action affects and any blocking obligations in broad categories. See [corrections](O1_ADMINISTRATION_GOVERNANCE.md). |

Use responsive single-column forms on narrow screens, visible labels, fieldsets, text status alongside icons, keyboard focus on errors and step transitions, and live announcements for save feedback. Preserve entered values during recoverable failures. Add a typed `organization-onboarding` namespace for Haitian Creole, French, English and Spanish, matching the existing `locales` and parity checker. Localize label, status, error, help and confirmation keys, dates and plurals. Have fluent reviewers check the distinction between informal, pending registration and verified identity.

## Persistence and lifecycle

- O2 proposes private `organization_onboarding_intents`: UUID, subject UUID FK to Auth, pathway, stage, bounded typed draft fields, optional target organization FK, optional completed organization FK, version, timestamps. Enforce one open intent per subject with a partial unique index. A completed record may remain as a receipt while a member later opens another. No organization row for a preference, incomplete wizard, private draft, discovery or abandoned intent.
- Pathway is editable. Organization stages: `selected → drafting → awaiting_identity → ready → authority_pending → completed`, with `cancelled` and resume/reassessment on hold, stale evidence or changed target. Drafting may continue while awaiting identity. Readiness derives from live checks and is never a client override. Individual default needs no record for legacy members. Save an explicitly selected pre-auth preference as an Auth metadata hint or actor-bound server receipt; copy it once into authoritative storage after confirming the live account. Later metadata cannot overwrite the intent. On a different device, resume from the saved server state or let the authenticated member choose again.
- O4 extends `private.organizations` with `claimed_registration_status` (unknown, informal_unregistered, pursuing_registration, registered), default unknown for legacy records. Keep confirmed registration in a private versioned determination linked to organization, jurisdiction, registry if applicable, scoped evidence reference, reviewer, timestamps and outcome; at most one current finding per organization. Status, kind, operational restrictions and verification remain independent. Map charities into nonprofit plus a separately confirmed charity recognition, not a self-declared badge. Keep education, business, media, NGO, foundation and public institution kinds. Treat community organization as a proposed kind if discovery needs it, with informal or pursuing status available across appropriate kinds. Government categories take a separate reviewed path using official authority evidence and independent review. Do not infer registration from country, category, name or tax status.
- The current organization verification column stores unverified, verified or revoked. Derive pending/rejected application status from the application visible to authorized managers. Keep any public label keyed to current approved provenance. Never project evidence, unconfirmed recognition, or reviewer notes to the directory. Revisit existing identity field locks when adding registration fields and include material fields in the reviewed snapshot.

## Proposed API and transaction boundary

Under `/api/v1`: GET/PUT `/me/organization-onboarding` for resume and bounded draft saves; POST `/me/organization-onboarding/:id/complete` for new setup or existing claim dispatch; POST `/me/organization-onboarding/:id/change-path` and matching admin correction action; reuse verification and invitation endpoints after their live checks. Keep a single canonical completion transaction shared with the legacy institution create route in O4. Existing claim remains pending until the approved claim decision establishes authority. Candidate duplicate names are hints; the handle is reserved only at canonical creation. Upgrade the existing public, search, follow, logo and account projections together if introducing any new visibility flag.

Share discriminated TypeScript DTOs under `packages/shared`: `SignupPath`, `OrganizationIntentStage`, `RegistrationClaim`, `OrganizationSetupCommand`, `OrganizationSetupReceipt` and stable error codes. Derive actor from verified session and scope from the database. Use strict schemas, bounded input, UUID idempotency key and expected version. Scope receipts by actor, action and key, with canonical request digest. Exact retries return the prior receipt after validating current read authority; changed payload rejects. Check eligibility, target revision, open claims and membership inside the transaction. Serialize per subject then organization in a documented order shared with competing commands. Use unique constraints as the final concurrency guard, write audit and in-app notice outbox atomically, and treat conflicting writes as reload-and-retry.

Enable RLS on new private tables, revoke direct application grants, and expose narrow RPCs consistent with the current API boundary. Set an empty search path and schema-qualify references in security definer functions, explicitly revoke PUBLIC execute and grant only the intended role. For service-only commands, Fastify verifies current session and scoped MFA where required, then supplies server-derived actor/assurance. SQL rechecks live authority and locks the protected state. Responses contain bounded subject-safe projections. Use `IDENTITY_REQUIRED`, `AUTHORITY_REQUIRED`, `HANDLE_UNAVAILABLE`, `STALE_VERSION`, `IDEMPOTENCY_CONFLICT`, `DEPENDENCY_BLOCKED`, `MFA_REQUIRED`, and nondisclosing `NOT_FOUND` for inaccessible targets. See [threats and tests](O1_SECURITY_THREAT_MODEL.md).
