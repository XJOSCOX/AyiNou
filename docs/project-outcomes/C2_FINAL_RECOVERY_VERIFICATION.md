# C2 final recovery verification

The rehearsal runs inside an isolated disposable Supabase project. It takes a PostgreSQL custom dump with no on-disk plaintext artifacts produced by the runner. It restores into a uniquely named database initialized from template0 in the disposable container. The application remains connected to its original test database. It compares migration history and record fingerprints, tests no direct table access and backend-only Impact RPC execution, and verifies existing invalidated disclosures, suppressed reports and closed gates. After verification the rehearsal removes only the restore database and clears the in-memory backup buffer.

This validates PostgreSQL recovery and the database-backed record model. A restored historical snapshot must stay quarantined until access is reconciled, pending revocations are replayed, sessions are invalidated as required, and current gates are confirmed. Provider backup access, region and point-in-time recovery objectives, private Storage media restoration, credential rotation, backup retention, recovery-point reconciliation and a supervised hosted rehearsal remain launch dependencies. Hosted records were outside the recovery rehearsal.

The revised isolated restore passed. The PostgreSQL custom dump was 11,535,606 bytes. Its SHA-256 was `2b3143337fa2383b4a10582f2275a1d0b9e7db59d5dbbb72418deef362f6be35`. The migrated schema, completed projects, linked needs, reviewed and challenged evidence records, disclosures, mappings, audit receipts and suppressed release fingerprints matched. The PostgreSQL rehearsal did not restore external Storage bytes. The existing disposable C2.2 test separately verifies case-bound access to database-backed evidence images.
