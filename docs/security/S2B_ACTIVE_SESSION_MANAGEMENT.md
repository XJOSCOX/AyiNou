# S2B active session management

Account Settings → Security shows the current session and the account's other sessions that Ayinou still accepts. Each entry displays the original provider sign-in time, effective S2A expiration and browser remember choice. The UI uses a random management reference and never returns a provider session ID, credentials, device fingerprint, location or last-activity estimate.

Targeted revocation and sign-out of other sessions are owner-bound and exclude the initiating session. The database serializes owner commands, pins the authenticated actor session and records revocation and its receipt together. A leadership account needs a current verified TOTP proof within the existing 15-minute window. Sign-out of other sessions by the Founder or Administrator also requires a same-session confirmation workflow. Local sign-out continues through Supabase Auth.

Supabase documents current, global and all-other sign-out scopes. Its client API provides neither a supported selected-remote-session revocation call nor a reliable last-activity feed used here. S2B uses Ayinou-side revocation for both new actions to keep their outcomes transactional. Each revocation shares the S2A policy row for the provider session and survives refresh rotation. Auth removes that row through the existing cascading dependency when it deletes the provider session. Until provider cleanup, the provider can still issue credentials for that session. Ayinou rejects them at its live boundaries. Direct Supabase Auth credential operations remain under provider policy. [Supabase sign-out](https://supabase.com/docs/guides/auth/signout) · [Supabase sessions](https://supabase.com/docs/guides/auth/sessions)

Revocation applies to sessions present when the command takes effect. Later independent sign-ins proceed normally. Requests already authorized before revocation may finish. The affected device can reauthenticate through normal sign-in. Session inventory only represents this application and the current account.
